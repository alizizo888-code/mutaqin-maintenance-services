# مشروع مُتقِن (MUTQAN) — نسخة PHP / MySQL

## 1. ما الذي تحتويه الحزمة؟

هذه النسخة تنظّم الملفات التي تم رفعها وتوفر أساساً يعمل على استضافة PHP + MySQL مثل Hostinger، بدون Node.js أو VPS.

- `index.php`: مدخل الدومين الرئيسي وواجهة العميل/الزائر بالعربية RTL، مع دليل الخدمات والتخصصات والتسجيل وطلب الخدمة.
- `backend/config/db.php`: اتصال PDO موحد بقاعدة MySQL، دون كتابة بيانات الاتصال مباشرة في ملفات API.
- `backend/api/api.php`: مسار توافق قديم محدود؛ قراءة بيانات العملاء والطلبات والفواتير تتطلب جلسة وصلاحيات مالك/عمليات، والتعديلات عبر واجهات النظام المحمية.
- `backend/api/portal.php`: تسجيل الدخول عبر `auth.php`، إنشاء طلبات الزائر والعميل، المحادثات، لوحة كل دور، اعتماد مزودي الخدمة، وتحديث حالة المهام.
- `backend/api/operations.php`: لوحة العمليات وإسناد يدوي للفني المتاح فقط؛ لا يوجد إسناد تلقائي.
- `backend/api/invoices.php`: واجهة فواتير محمية بجلسة وصلاحيات المالك/العمليات. توليد الفواتير أو رفع PDF آلياً ليس مكتملاً من واجهة العميل الحالية.
- `backend/upload/image-handler.php`: رفع صور محلية JPG/PNG/WEBP بحجم أقصى 5MB، مع جلسة وصلاحية وCSRF وتقييد بحسب الطلب المرتبط.
- لا يوجد حالياً مسار نشط لرفع PDF الفواتير؛ لا تعتمد على معاينة الفواتير القديمة حتى استكمال هذه الوظيفة.
- `database/schema.sql`: مخطط قاعدة بيانات مُنظم يتضمن الأنظمة الخمسة، وفئات الخدمات، وحقول حالة الطلب وموقعه والتواريخ.
- `database/schema-original.sql`: نسخة من ملف SQL الأصلي الذي رفعته، بدون تعديل.
- `frontend/prototypes/`: الواجهات HTML الأصلية بعد تسميتها بأسماء واضحة، وتظهر عليها علامة «معاينة تجريبية».
- `reference/`: نسخة ZIP الأصلية وكل الملفات المنفصلة الأصلية كما وصلت، للرجوع إليها.

## 2. التثبيت على Hostinger

1. أنشئ **قاعدة بيانات MySQL جديدة وفارغة** من لوحة Hostinger. لا تستورد `database/schema.sql` فوق قاعدة تشغيل تحتوي بيانات مهمة.
2. افتح phpMyAdmin واختر قاعدة البيانات الجديدة، ثم استورد `database/schema.sql`.
3. انسخ محتويات مجلد المشروع إلى `public_html` للدومين أو المجلد المستهدف، لا ترفع مجلد `mutqan-php` كطبقة إضافية إن كنت تريد الصفحة على الدومين مباشرة.
4. انسخ `backend/config/config.local.php.example` إلى `backend/config/config.local.php`، ثم أدخل `DB_HOST` و`DB_NAME` و`DB_USER` و`DB_PASS` من Hostinger. لتوجيه واتساب مباشرة إلى الشركة، ضع رقم WhatsApp Business الدولي في `WHATSAPP_BUSINESS_NUMBER`. لا ترفع `config.local.php` إلى GitHub.
5. تأكد من استخدام PHP 8.1 أو أحدث وتوفر PDO MySQL وFileinfo. يحتاج مجلد `uploads/` إلى صلاحية كتابة من PHP؛ ابدأ بصلاحيات المجلد الافتراضية المناسبة للاستضافة ولا تمنحه صلاحية 777.
6. افتح الدومين. إذا لم تضبط قاعدة البيانات بعد، فستبقى الواجهة ظاهرة مع حالة «بانتظار إعداد قاعدة البيانات»، ولن يتم تسجيل الطلبات حتى ينجح الاتصال.

## 3. اختبار API

- كتالوج الواجهة العامة: `GET /backend/api/portal.php?action=services`.
- تسجيل طلب زائر/عميل: `POST /backend/api/portal.php?action=create_request` مع `service_category`, `service_name`, `full_name`, `phone`, `address`, `issue`، ويمكن إضافة `latitude`, `longitude`, `priority`؛ الطلبات المعدّلة تتطلب CSRF/session.
- لوحة الدور الحالي: `GET /backend/api/portal.php?action=dashboard`، وتتطلب جلسة نشطة.
- الإسناد اليدوي: `POST /backend/api/portal.php?action=assign_request` مع `request_id` و`technician_user_id`، وصلاحية مشرف العمليات/المالك وCSRF. لا يوجد اختيار فني تلقائي.
- لوحة عمليات بديلة: `GET /backend/api/operations.php?action=dashboard`، وتتطلب جلسة مشرف عمليات أو مالك.
- الفواتير: `GET/POST /backend/api/invoices.php` (إنشاء مسودة عبر `action=create`، ثم إصدارها عبر `action=issue` بعد حفظ التوقيع وملف PDF).
- رفع PDF لفاتورة موجودة: `POST /backend/upload/invoice-pdf-handler.php` بصيغة `multipart/form-data`: `invoice_id`, `pdf_file`، مع ترويسة `X-Admin-Token`. هذا المعالج يرفع PDF؛ ولا يقوم بإنشاء فاتورة PDF من الصفر.
- رفع صورة محلية: `POST /backend/upload/image-handler.php` بصيغة `multipart/form-data`: `image_file`, `owner_type`, `owner_id`, `field_role`، مع ترويسة `X-Admin-Token`.

تدفق الفاتورة الحالي: أنشئ مسودة فاتورة، ثم ارفع صورة التوقيع عبر `image-handler.php` باستخدام `owner_type=invoice`, `owner_id=رقم_الفاتورة`, `field_role=signature`، وارفع ملف PDF المُجهز مسبقاً عبر معالج PDF، وبعد ذلك أرسل `{ "action": "issue", "invoice_id": رقم_الفاتورة }` إلى `invoices.php`.

التعديلات الإدارية في واجهات البوابة الجديدة تتطلب جلسة خادمية وصلاحية مناسبة ورمز CSRF. لا تضع كلمات المرور أو ملفات الإعداد المحلية في HTML أو JavaScript أو GitHub.

## 4. أسماء الأنظمة المعتمدة

| الجدول | الغرض |
|---|---|
| `system_1_clients` | بيانات العملاء |
| `system_2_technicians` | الفنيون وتخصصاتهم وتقييماتهم وحالاتهم |
| `system_3_requests` | طلبات الصيانة والموقع والأولوية والحالة وصور قبل/بعد |
| `system_4_services` | قائمة الخدمات والأسعار وربطها بفئة |
| `system_5_invoices` | الفواتير والمبالغ والخصومات والتوقيع |
| `image_data_bindings` | ربط الملفات المحلية بالسجلات وبصمات SHA-256 |

## 5. حدود النسخة الحالية — مهم قبل النشر الفعلي

- صفحات `frontend/prototypes/*.html` معاينات للتصميم، وقد كانت تعتمد على بيانات وهمية داخل JavaScript؛ اللافتة أعلى كل صفحة توضح ذلك. **غرفة العمليات وصفحة الفواتير في هذه المعاينات غير متصلتين بعد بقاعدة البيانات.**
- تم توصيل الصفحة الرئيسية بنموذج طلب الصيانة وقائمة الخدمات. أما تسجيل دخول الموظفين والصلاحيات التفصيلية وتجربة إدارة الطلبات من الواجهة فتحتاج مرحلة تنفيذ منفصلة.
- نسخة React الأصلية تعتمد على SDK خاص بمنصة Whacka غير موجود في ZIP. حفظنا الأرشيف للرجوع إليه ولم نخلط ملفات React في مسارات مشروع PHP.
- معالج الفواتير يستطيع حفظ المسودة وربط التوقيع ورفع ملف PDF مُجهز مسبقاً، لكنه لا ينشئ PDF ضريبياً من الصفر. توليد PDF آلياً ودمج واتساب الرسمي يحتاجان استكمالاً واختباراً.
- أُضيف الآن نظام جلسات وأدوار وCSRF وسجل تدقيق لواجهات البوابة الجديدة. قبل الإطلاق الفعلي ما زال يلزم ضبط حسابات الإنتاج، ومحدد معدل طلبات على مستوى الخادم، وسياسة احتفاظ بالصور، واختبارات على قاعدة Hostinger الفعلية، وربط SMS/OTP إن كانت مطلوبة.
- ملف `database/schema.sql` مصمم لقاعدة جديدة فارغة. `CREATE TABLE IF NOT EXISTS` لا يغيّر بنية جداول قديمة موجودة مسبقاً؛ لا تستخدمه كترقية تلقائية لقاعدة قديمة.

## 6. الأمان والبيانات

- كلمات المرور ورموز الإدارة غير مضمنة في ملفات الواجهة.
- رسائل خطأ PDO التفصيلية تذهب إلى سجل أخطاء PHP ولا تُعرض للزائر.
- الصور تُقبل من ملفات محلية فقط، وتُرفض الروابط الخارجية، وتُولّد بصمة SHA-256 بعد الحفظ.
- `uploads/.htaccess` يمنع تنفيذ امتدادات PHP الشائعة داخل مجلد الملفات.
- احتفظ بنسخة احتياطية من قاعدة البيانات والملفات قبل أي تحديث.

## 7. رحلة العميل والبوابات المنفصلة (إضافة 2026-10-17)

### الصفحة الرئيسية والدومين
- index.php هو مدخل الدومين ويعرض كتالوجاً عربياً RTL للخدمات كزائر: التكييف والتبريد، السباكة، الكهرباء والإضاءة، النجارة والأثاث، المقاولات والترميم، الخزانات، نقل العفش، الدش والستالايت، الصيانة العامة، والتنظيف والخدمات المساندة.
- بعد اختيار القسم يختار الزائر تخصصاً داخلياً، ثم يختار إحدى الطرق: متابعة كزائر، تسجيل حساب عميل، أو تقديم طلب انضمام كمزود خدمة.
- الواجهة متجاوبة مع الهاتف، وGPS عبر متصفح HTTPS بعد موافقة المستخدم؛ إذا رفض الإذن يمكن إدخال العنوان يدوياً. روابط الموقع تُفتح في خرائط Google دون مفتاح API.
- طلب الزائر يُحفظ برمز وصول للمحادثة في جلسة المتصفح. إذا مسح المستخدم بيانات الجلسة فقد يفقد رابط المحادثة؛ لا يوجد OTP SMS حالياً لاسترجاع الطلب.

### المستخدمون والأدوار
- ali: حساب عميل تجريبي.
- ali1: حساب فني تجريبي.
- ali2: حساب مشرف عمليات تجريبي.
- ali3: حساب مالك تجريبي.
- حسابات الفريق التجريبية في ملف migration لها كلمات مرور مؤقتة مشتقة إلى hashes، وجميعها تُجبر على تغيير كلمة المرور عند أول دخول. غيّرها قبل أي استخدام حقيقي؛ لا تضع كلمات المرور الفعلية في GitHub.
- التسجيل العام لا يسمح بإنشاء مالك أو مشرف عمليات أو فني معتمد. تسجيل مزود الخدمة ينشئ طلباً بحالة pending ويرسل إشعاراً داخلياً للمالك؛ فقط المالك يستطيع اعتماده كفني.
- اعتماد مزود الخدمة لا يوزع المهام عليه. مشرف العمليات أو المالك يختار الفني صراحةً عند الإسناد. الفني يرى المهام المسندة إلى حسابه فقط، ويحدّث مراحل المهمة حتى إرسالها لمراجعة الإغلاق. العمليات/المالك يعتمدان الإغلاق أو يعيدانها للفني.
- واجهات API القديمة التي كانت تقرأ بيانات داخلية دون جلسة تم تقييدها. الواجهات العامة لا تعرض سجلات العملاء أو الطلبات أو الفواتير.

### تثبيت قاعدة البيانات لأول مرة
1. خذ نسخة احتياطية من قاعدة البيانات والملفات الحالية.
2. إذا كانت قاعدة جديدة فارغة، استورد database/schema.sql أولاً.
3. افتح database/migrations/20261017_role_based_portals.sql ونفّذه مرة واحدة فقط بعد الجداول الخمسة الموجودة. هذا الملف يضيف جداول الحسابات والإشعارات والمحادثات والتدقيق، ويضيف حقول الحالة والموقع والإسناد إلى الطلبات ويربط حساب الفني التجريبي بسجل الفنيين.
4. انسخ backend/config/config.local.php.example إلى backend/config/config.local.php واضبط DB_HOST وDB_NAME وDB_USER وDB_PASS. لا ترفع الملف المحلي المحتوي على بياناتك إلى المستودع.
5. أضف رقم واتساب الشركة الدولي في WHATSAPP_BUSINESS_NUMBER داخل config.local.php (أرقام فقط مع مفتاح الدولة) حتى تنتقل روابط واتساب مباشرة إلى الشركة. إذا تركته فارغاً فسيُفتح واتساب برسالة جاهزة لكن دون تحديد رقم الشركة.
6. ارفع محتويات الحزمة إلى جذر الدومين بحيث يوجد public_html/index.php وpublic_html/assets/mutqan.js وpublic_html/backend/api/auth.php وpublic_html/backend/api/portal.php.
7. سجّل دخول الحسابات التجريبية مرة واحدة وغيّر كلمات المرور فوراً. اختبر طلب زائر، تسجيل عميل، طلب مزود خدمة، موافقة المالك، والإسناد اليدوي من العمليات.

### حدود مهمة قبل التشغيل التجاري
- إشعارات المالك والفني حالياً إشعارات داخلية في النظام وتظهر عند تحديث لوحة التحكم؛ لا يوجد Push أو SMS/OTP متصل بخدمة خارجية.
- اختيار الموقع يتطلب موافقة GPS، وتحديث موقع الفني يتم عند الضغط على زر تحديث الموقع، وليس تتبعاً مستمراً في الخلفية.
- واتساب يعتمد على رقم الشركة الذي تضبطه محلياً. المحادثة داخل النظام تحفظ الرسائل بقاعدة البيانات.
- صفحات frontend/prototypes ونسخة React تحت react-export تظل معاينات/نسخاً تجريبية منفصلة؛ المسار الفعلي للدومين في هذه الحزمة هو index.php مع واجهات PHP الجديدة.
- ملف migration ليس ترقية قابلة للتكرار؛ لا تعِد تشغيله بعد نجاحه لأن أوامر ALTER TABLE ستتكرر.
